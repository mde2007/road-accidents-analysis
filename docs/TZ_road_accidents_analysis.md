# ТЗ: Анализ дорожно-транспортных происшествий (ДТП)

Геоанализ, SQL-витрины, статистика и модель риска на открытых данных.

---

## 1. Цель проекта

Построить воспроизводимый аналитический проект: открытые данные о ДТП → очистка в Python → хранение в PostgreSQL → SQL-аналитика → геоанализ на картах → ML-модель тяжести ДТП → интерактивный дашборд.

**Что получите в итоге:**
- репозиторий на GitHub с понятным README, картами и выводами;
- навыки, которые просят в вакансиях аналитика: SQL, pandas, визуализация, статистика, геоданные, базовый ML, Docker, Git;
- проект с наглядным результатом (карты и дашборд), который легко показать на собеседовании.

**Бизнес-вопросы, на которые отвечает проект:**
1. Когда (час, день недели, месяц) происходит больше всего ДТП и когда они наиболее тяжёлые?
2. Как погода, освещённость, состояние покрытия и тип дороги связаны с тяжестью последствий?
3. Где находятся «горячие точки» (участки с повышенной аварийностью)?
4. Как меняется картина по годам?
5. Какие условия сильнее всего связаны с тяжёлыми исходами (погибшие и тяжело раненые)?
6. Можно ли по условиям ДТП оценить вероятность тяжёлого исхода?

## 3. Данные

### Основной вариант: Великобритания, STATS19 (Department for Transport)

Официальные открытые данные о ДТП с пострадавшими, публикуются в виде CSV на data.gov.uk (искать «Road Safety Data» / «STATS19»). Состоят из трёх связанных таблиц:

| Таблица | Содержит |
|---|---|
| `collision` | одна строка на ДТП: дата, время, координаты, тяжесть, погода, освещённость, покрытие, тип дороги, ограничение скорости, район |
| `vehicle` | транспортные средства, участвовавшие в ДТП: тип, манёвр, возраст водителя |
| `casualty` | пострадавшие: возраст, пол, тяжесть, тип участника движения |

Таблицы связываются по идентификатору ДТП (`collision_index`).

**Объём для проекта:** последние 5 лет (порядка сотен тысяч записей). Точные названия колонок и кодов смотрите в официальном руководстве по данным (data guide), которое лежит на той же странице. Оно содержит расшифровку числовых кодов.

**Особенности данных, о которых нужно знать заранее:**
- Категории закодированы числами (например, тяжесть: 1 = fatal, 2 = serious, 3 = slight). Значение `-1` и некоторые другие обычно означают «данные отсутствуют».
- Это только ДТП с пострадавшими, поэтому лёгкие аварии без травм сюда не попадают.
- В данных нет информации об интенсивности движения, поэтому «где больше ДТП» не равно «где опаснее». Это нужно честно описать в выводах.

### Запасной вариант
Российские данные о ДТП (Госавтоинспекция, сторонние агрегаторы) тоже существуют, но доступность и формат нужно проверять отдельно. Если выберете их, обсудите структуру с ментором на первой неделе.

### Неделя 4. SQL-аналитика и витрины

**Цель:** научиться отвечать на бизнес-вопросы запросами и собрать витрины.

**Шаги (идти от простого к сложному, каждый запрос сначала описать словами):**
1. Базовые запросы: `SELECT`, `WHERE`, `ORDER BY`, `LIMIT`. Сколько ДТП по годам?
2. Агрегации: `GROUP BY`, `COUNT`, `AVG`, `HAVING`. Доля тяжёлых ДТП по часам, дням недели, типам дорог.
3. Соединения: `JOIN` между таблицами ДТП и справочниками. Разница между `INNER` и `LEFT`.
4. CTE (`WITH`): разбить сложный запрос на читаемые части.
5. Оконные функции: `ROW_NUMBER`, `RANK`, `LAG`, скользящее среднее. Например, топ-10 районов по тяжёлым ДТП в каждом году; изменение числа ДТП год к году.
6. Условная агрегация: `CASE WHEN`, `FILTER`.
7. Создать 3-4 витрины (`VIEW` или таблицы): ДТП по времени, ДТП по условиям (погода + освещённость + покрытие), ДТП по районам, динамика по годам.

**Что изучить:** порядок выполнения SQL-запроса, `COALESCE`, `NULLIF`, `date_trunc`, `PARTITION BY`, `CREATE VIEW`, `CREATE INDEX`.

**Подводные камни:** деление целых чисел (потеря дробной части); путаница `WHERE` и `HAVING`; `COUNT(*)` против `COUNT(column)`; потеря строк из-за `INNER JOIN`.

### Неделя 7. ML-модель: оценка тяжести ДТП

**Цель:** построить модель, которая по условиям ДТП оценивает вероятность тяжёлого исхода (погибшие или серьёзные травмы), и грамотно её оценить.

**Шаги:**
1. Сформулировать задачу: бинарная классификация («тяжёлое / лёгкое ДТП»). Обсудить, почему это интересная и корректная постановка.
2. Выбрать признаки, доступные **на момент ДТП**: время, день недели, погода, освещённость, покрытие, тип дороги, ограничение скорости, число ТС, городская/сельская зона и т.д. Не использовать признаки, которые известны только после исхода (утечка данных, data leakage).
3. Разделить данные на train/test. Подумать, как: случайно или по времени (последний год в тест). Для задачи с временем разумнее вариант по времени.
4. Построить **бейзлайн**: например, всегда предсказывать самый частый класс и простая логистическая регрессия.
5. Учесть дисбаланс классов (тяжёлых ДТП значительно меньше): стратифицированное разбиение, веса классов.
6. Обучить градиентный бустинг (LightGBM или CatBoost), подобрать несколько параметров.
7. Оценить правильными метриками: ROC-AUC и особенно PR-AUC, precision/recall, матрица ошибок. Accuracy здесь почти бесполезна, объяснить почему.
8. Проверить калибровку вероятностей.
9. Интерпретировать: важность признаков, SHAP. Сформулировать, какие условия связаны с повышением риска.
10. Описать ограничения: нет данных о трафике, нет данных о поведении водителей, связь не равна причинности.
11. Сохранить модель, оформить `04_model.ipynb`, `src/features.py`, `src/model.py`.

**Что изучить:** train/test split, stratify, data leakage, `class_weight`, ROC-AUC vs PR-AUC, кросс-валидация, SHAP, калибровка.

**Подводные камни:** утечка данных; хорошая accuracy при бесполезной модели; подбор параметров по тестовой выборке; категориальные признаки с большим числом значений.

**Результат недели:**
- [ ] модель лучше бейзлайна по PR-AUC (с цифрами в README)
- [ ] график SHAP или важности признаков и интерпретация словами
- [ ] раздел «Ограничения» в README

**Самопроверка:** почему accuracy 95% может означать плохую модель? Что такое утечка данных и где она могла бы возникнуть здесь?
